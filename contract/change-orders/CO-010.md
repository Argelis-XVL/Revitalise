## Scope

Build the `REV | Finance | Capture Payment` flow, minimum behaviour only. When a `rev_payment` row is marked final
(`rev_isfinalpayment = true`):

1. set `rev_grant.rev_finalpaymentdate` on the payment's grant, and
2. set the parent application's `rev_status` to 11 "Grant Paid" (`rev_applicationstatus` option set).

This closes TAD risk **A-R56**: `rev_finalpaymentdate` is written by nothing today, so the six-year retention clock
(TAD §3.4, ADR-004) never starts for any grant. It is a compliance gap, not only an automation gap.

**Not part of this order, flagged only:** the pre-issue duplicate-payment re-check (Automation #7 / FR-023 second
call site). TAD §5.11 lists it among the three things the flow "would have" done, so it may be read as bound to this
flow. This decision does not add it. Verifying that hook stays with `wbs:8.5`. If it is wanted in this flow it needs a
separate decision and a re-price.

## Why this is a change order, not rework against an existing task

No accepted task covers a flow that writes the grant or application on final payment. `wbs:8.3` is the capture form,
`8.4` is the Payment-to-Grant and payee relationship, `8.5` tests the finance flow. None of their descriptions in
`contract/wbs.json` names a status change or a retention date being set by automation. The reviewer's reason for not
billing, "I thought this was already included", is a statement about expectation, not about the accepted text: the
work is unbilled by his decision, and it is still recorded as a change order so it has a task id (C-COM-002).
