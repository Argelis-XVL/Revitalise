## Scope

Per the reviewer's own routing (`docs/plans/emily-review-feedback-2026-09-plan.md` line 1053, EF-03
Δ4): a derived city identifier, because the applicant's own typed `rev_towncity` value is unreliable
for funder reporting. No city derivation exists today — only region is derived from postcode
(`PostcodeRegionMap`), and that map holds regions, not settlements.

- A ~3,000-row outward-code reference table, same shape as `PostcodeRegionMap` and CO-004's
  generator, keyed on postcode outward code, sourced from the client's own delivered export
  (`Postcode Details.xlsx`, *Main Postal Town / City* column) — not ONSPD, which does not carry
  this column in the form the plan specifies.
- A lookup step at intake writing the derived value to a new column on Applicant.
- **A miss stays a miss**: no alphanumeric London outward code (`EC1A`, `WC2H`, `SW1A`, …) exists in
  the client's file, so those applications must resolve to `null` plus the existing Intake Review
  Note mechanism (EF-20), never a nearest-guess — same rule the plan sets for EF-41 (line 632).

## Why this is a change order, not rework

No task in `contract/wbs.json` names a city reference table or a city-derivation step. This is new
capability, not a defect against an existing deliverable — city has never been derived from postcode
in this build. Plan citation: line 1053 (EF-03 detail, Δ4), sized **M** there (*"was L"*, reduced
once the client's file confirmed the lookup was specifiable).

## Quality limits carried over from the source file (not resolved by this order)

Per line 1053: no alphanumeric London outward codes in the file (handled by the miss-handling rule
above), and the file's *County* column is not a county in 30% of rows — irrelevant to city derivation
itself, noted here only because it is the same file EF-40/CO-004 also draws quality caveats from.
